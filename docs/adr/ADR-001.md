# ADR-001: Adaptador JDBC para PedidoRepository en lugar de JPA

## Estado
Aceptado

## Contexto
El puerto de dominio `PedidoRepository` (interfaz definida en `pedido/domain/`) no tenía
ninguna implementación concreta en el repositorio. Esto provocaba que el contexto de Spring
fallara al arrancar en cualquier test que cargara la aplicación completa (`@SpringBootTest`),
ya que el bean `TestingAPI` requiere `PedidoRepository` como dependencia inyectada y no
existía ningún candidato para satisfacerla.

Adicionalmente, se identificó que los enums de dominio (`EstadoPedido`, `TipoEntrega`) no
coinciden con los valores reales usados en la tabla `pedido` de la base de datos (por
ejemplo, el dominio usa `CONFIRMADO` mientras la base de datos usa `PAGADO`).

## Decisión
Se implementó `PedidoRepositoryJdbcAdapter`, un adaptador basado en `JdbcTemplate` (en vez
de Spring Data JPA), que:
- Implementa todos los métodos del puerto `PedidoRepository`.
- Traduce explícitamente entre los valores de enum del dominio y los valores reales de la
  base de datos mediante métodos de mapeo dedicados (`estadoDbADominio`/`estadoDominioADb`).
- Se registra como `@Component`, permitiendo que Spring lo inyecte automáticamente donde
  se requiera el puerto `PedidoRepository`.

Se optó por JDBC en lugar de JPA por consistencia: el resto del módulo `pedido`
(`CarritoController`, `PedidoClienteController`) ya usa `JdbcTemplate` directamente contra
las mismas tablas, por lo que introducir un nuevo modelo de persistencia (entidades JPA)
para un solo adaptador habría añadido una segunda estrategia de acceso a datos sin
necesidad real.

## Consecuencias
- Positivas: el contexto de Spring carga correctamente; las pruebas BDD/Cucumber
  (`TestingAPI`) ya pueden ejecutarse; el puerto de dominio queda con una implementación real,
  cerrando parcialmente la brecha de arquitectura hexagonal.
- Negativas (deuda técnica reconocida): el flujo real de compra del sistema
  (`CarritoController`, `PedidoClienteController`) continúa accediendo a la base de datos
  directamente vía JDBC, sin pasar por el puerto `PedidoRepository` ni por sus adaptadores.
  Esto significa que el aislamiento del dominio para el módulo de pedidos es parcial: existe
  el puerto y su adaptador, pero no todo el sistema los usa todavía. Se registra como trabajo
  futuro unificar el acceso a datos de pedidos a través del puerto de dominio.
